# 7. Fixing Issues (Phase 4 Post-Integration Hardening)

This document outlines the final technical implementation plan for **Phase 4 Post-Integration Hardening** in FOT Hub. The goal of this task is to enforce strict user data isolation, implement date awareness/currentness, measure and optimize election manifesto retrieval, stabilize tool result summaries with diagnostic logging, enforce vote tally grounding, eliminate repetitive boilerplate closings, and execute comprehensive regression testing.

## Hardening Component Breakdowns

### 🔴 H1 — User Data Isolation (Security Boundary — Highest Priority)
* **Security Boundary Architecture**:
  * **Intent Router**: Maps user text to tool intent (`COMPLAINT_STATUS`, `NOTIFICATIONS`). Does **NOT** act as a security boundary.
  * **Tool Executor (`toolExecutor.js`) & MongoDB Queries**: Operates as the sole authoritative security boundary using `userContext._id`.
* **Implementation Rules**:
  * `getComplaintStatus`: Filter strictly by `submittedBy: userContext._id`.
  * `getNotifications`: User-private components (complaint updates) must be scoped strictly to `submittedBy: userContext._id`. Public campus announcements remain globally readable.
* **Mandatory Two-User & Cross-ID Probing Test**:
  * Setup: User A (Complaints A1, A2), User B (Complaints B1, B2).
  * Assert: User A receives ONLY A1 and A2; User B receives ONLY B1 and B2.
  * Explicit Probing: User A calling `getComplaintStatus({ complaintId: B1._id })` MUST return empty/not found; User B calling `getComplaintStatus({ complaintId: A1._id })` MUST return empty/not found.
  * *Early Checkpoint*: If this test fails, all other hardening work stops until 100% resolved.

---

### 🔴 H2 — Date Awareness & Currentness
* **Dynamic Current Date Injection**: Inject `Current Date: YYYY-MM-DD` (e.g. `2026-08-16`) into prompt context in `promptBuilder.js`.
* **Temporal Reasoning Rules**: Define rules in `SYSTEM_ROLE` for temporal keywords (`latest`, `current`, `today`, `upcoming`, `recent`, `this year's`):
  * Do not describe a past event as upcoming or current.
  * If retrieved information is historical, explicitly identify it as historical.
  * Do not assume an old election is the current election.
  * For "latest" or "upcoming", prefer information whose dates/status are consistent with the current date.
  * If no current information exists, explicitly state that the available knowledge is historical or insufficient.
* **Test Queries**:
  * `"What are the latest announcements?"`
  * `"What is the most recent announcement?"`
  * `"Is the 2025 Student Union Election still upcoming?"` (Verifies system identifies 2025 election as historical relative to today's date).

---

### 🟠 H3 — Election Candidate & Manifesto Retrieval
* **Measure Retrieval Score First**: Do **NOT** automatically lower `SIMILARITY_THRESHOLD` from `0.65` to `0.55` upfront. Measure current retrieval score and inspect candidate query logs first:
  ```text
  Query: "What is Nimal's manifesto?"
  Retrieved:
    1. source=election, sourceId=..., score=0.71
    2. source=election, sourceId=..., score=0.63
  ```
  Adjust threshold only if candidate document is being excluded by the threshold.
* **Candidate Text Structuring**: Format candidate text in `knowledgeDocumentBuilder.js` cleanly using actual model data only:
  ```text
  Election: FOT Student Union Election 2025
  Status: completed

  Candidate:
  Name: Nimal Perera
  Position: President
  Manifesto: Focus on lab facilities and student communication.
  ```

---

### 🟠 H4 — LostFound Stability & Diagnostic Logging
* **Resilience Summary Flow**:
  * `Tool Call` → `Tool Executor` → `Tool Result` → `Gemini TEXT-ONLY Follow-Up` (omitting `functionDeclarations`) → `Final Answer`.
  * Fallback Path (if summary generation fails): `Tool Result` → `Direct Safe Formatter` → `Final Answer`.
* **Tool Search Filter Resilience (`toolExecutor.js`)**:
  * Fixed case-sensitivity mismatch on MongoDB schema categories (e.g. Gemini passing lowercase `"electronics"` vs model enum `"Electronics"`) using case-insensitive regex `{ $regex: /^category$/i }`.
  * Expanded single-field `title` queries into multi-field `$or` matches across `title`, `description`, and `category`. This prevents `0` records from returning when Gemini passes generic search keywords (e.g. `"electronic device"`).
* **Server-Side Diagnostic Logging**: Log actual backend error tracebacks (`console.error(err)`) on the server so developers have full diagnostic visibility while users receive a plain safe message.

---

### 🟡 H5 — Vote Tally Grounding & Confidentiality
* **System Rule**:
  * Candidate vote tallies and voter records are not part of the public retrieval knowledge.
  * Do **NOT** infer, estimate, reconstruct, or invent vote counts.
  * If asked `"How many votes did Nimal receive?"` or `"How many votes has each candidate received?"`, explicitly state that vote tally information is confidential and not available through the assistant's public knowledge.

---

### 🟡 H6 — Response Quality & Anti-Boilerplate
* **Anti-Boilerplate Instructions**:
  * Answer the user's question directly and concisely.
  * Do not automatically add a closing sentence after every response.
  * Do not repeatedly say `"Let me know if you need help with anything else."`.
  * Use a closing statement only when contextually useful (e.g., `"Your complaint has been submitted successfully."`).

## Comprehensive 8-Section Test Plan (`testPostHardeningFixes.js`)

* **Section A — User Isolation (Two-User Security Test)**: User A (Complaints A1, A2) vs User B (Complaints B1, B2). Asserts User A receives ONLY A1 and A2; User B receives ONLY B1 and B2. Asserts User A probing B1's `complaintId` returns empty/not found.
* **Section B — Date Awareness**: Queries `"What are the latest announcements?"`, `"What is the most recent announcement?"`, and `"Is the 2025 election upcoming?"`. Asserts 2025 records are recognized as historical.
* **Section C — Manifesto Retrieval**: Queries `"What is Nimal's manifesto?"`. Captures retrieved `source`, `sourceId`, and similarity score.
* **Section D — LostFound Stability**: Runs 10 repeated iterations of `"Did anyone find a blue umbrella?"`. Asserts 10/10 success without summary errors.
* **Section E — Vote Grounding**: Queries `"How many votes did Nimal receive?"`. Asserts response explicitly states vote tallies are confidential without fabricating numbers.
* **Section F — Anti-Boilerplate Quality**: Asserts responses do not append repetitive sign-offs.
* **Section G — Phase 3 Regression**: Full suite for `checkVotingEligibility`, `getComplaintStatus`, `getNotifications`, `submitComplaint`, `searchLostItems`, `searchAnnouncements`.
* **Section H — Phase 4 RAG Regression**: Announcement RAG, Election RAG, LostFound RAG, No-result retrieval, and Context injection.
