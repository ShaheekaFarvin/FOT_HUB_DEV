# 3. Tool Executor

Implement a centralized Tool Executor (`backend/ai/tools/toolExecutor.js`) that receives the standardized tool-call object (`{ name, arguments }`) produced by Topic 2, validates arguments and user context, delegates execution to existing backend models/controllers (`Announcement`, `Election`, `LostFound`, `Complaint`), enforces data isolation/ownership rules, and returns the operation result to the caller without creating new business logic or invoking Gemini.

## Backend Operations Mapping Table (Step 1)

| Tool Name | Target Backend Model / Operation | File Location | Execution Strategy & Security Scope |
| :--- | :--- | :--- | :--- |
| `searchAnnouncements` | `Announcement.find({ isActive: true, ... })` | [Announcement.js] | Queries active announcements with optional keyword search (`query`) and `category` filter. |
| `checkVotingEligibility` | `Election.find()` & `isDepartmentEligible()` | [Election.js] | Delegates to existing `isDepartmentEligible(userContext.department)` logic on active/ongoing elections. |
| `searchLostItems` | `LostFound.find({ status: 'active', ... })` | [LostFound.js] | Searches active lost & found items with optional keyword `query`, `type` (`lost`/`found`), and `category`. |
| `submitComplaint` | `Complaint.create(...)` | [Complaint.js]| Creates a student complaint record bound to `userContext._id` with target admin role (`targetAdminType`). Unit tests mock this mutation. |
| `getComplaintStatus` | `Complaint.find(...)` | [Complaint.js]| **Ownership Scoped**: Enforces `{ submittedBy: userContext._id }` filter even when `complaintId` is passed (unless user is authorized admin). |
| `getNotifications` | `Announcement.find(...)` & `Complaint.find(...)` | [Announcement.js] | Aggregates recent announcements and notification updates relevant to the authenticated user (`userContext._id`). |

## Proposed Changes

### Backend AI Module

#### [NEW] [toolExecutor.js]

- Export `executeTool(toolCall, userContext)`.
- **Validation Pipeline**:
  1. Validate `toolCall` object structure (`name`, `arguments`).
  2. Verify `name` against `getAvailableTools()` from `toolRegistry.js` (reject unknown tools with `{ success: false, error: 'Unknown tool: ...' }`).
  3. Validate required arguments (e.g. `submitComplaint` requires `title` and `description`).
  4. Verify `userContext` for user-scoped tools (`submitComplaint`, `getComplaintStatus`, `checkVotingEligibility`, `getNotifications`).
- **Execution & Security Delegation**:
  - Dispatch call to matching backend model/operation based on the mapping table.
  - Enforce user data isolation (e.g. student A cannot query student B's complaint).
- **Output Contract**:
  - Success: `{ success: true, data: ... }`
  - Error: `{ success: false, error: '...' }`
- **Strict Boundary**:
  - NO custom business logic creation.
  - NO Gemini API calls.
  - NO process crashes on database errors (catches exceptions gracefully).
