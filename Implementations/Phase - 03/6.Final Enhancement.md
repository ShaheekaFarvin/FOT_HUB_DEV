# Implementation Plan: AI Behavior Layer Improvements (Phase 3)

Improve the Phase 3 **AI Behavior Layer** (tool selection, optional argument handling, response quality, formatting, and error wording) while strictly preserving the intact, working Phase 3 infrastructure (Gemini function calling, Tool Executor, Tool Result Handler, Gemini follow-up cycle, Conversation Memory, Context Builder, Role Verifier, and Intent Router).

---

## User Review Required

> [!IMPORTANT]
> **Strict Architecture & Contract Preservation**:
> * No changes to Context Builder, Role Verifier, Intent Router, Conversation Memory, Tool Executor, or controller pipeline.
> * `getAvailableTools()` descriptions in `toolRegistry.js` remain strictly unchanged to preserve the Phase 2 contract.
> * Optional parameter guidance is added solely to parameter schemas within `getGeminiFunctionDeclarations()`.

> [!NOTE]
> **Optional Parameter Handling**:
> * Parameter-specific guidance instructs Gemini that `electionId`, `complaintId`, and `unreadOnly` are optional.
> * `promptBuilder.js` instructs Gemini to invoke tools immediately (e.g. `checkVotingEligibility({})`) for general queries like "Can I vote?" or "What's my complaint status?" without prompting the user for optional IDs.

---

## Observed Behavior & Diagnostic Strategy

### Observed Behavior / Suspected Cause
* **Observation**: Gemini may be interpreting optional parameters as mandatory in certain conversational contexts (e.g., requesting an `electionId` or `complaintId` before calling tools), and the final Gemini response may be receiving tool results in a form that is difficult to summarize cleanly or formatting bullet lists poorly.
* **Diagnostic Protocol**: Before modifying backend logic, verify the complete execution flow (`Gemini function call` → `Tool Executor` → `tool result` → `Tool Result Handler` → `second Gemini response`) using test executions and log inspection for `getComplaintStatus` and `getNotifications` to confirm the exact failure layer.

## Detailed Component Changes

### 1. Prompt Builder & System Instructions
#### [MODIFY] [promptBuilder.js]
* **Tool Selection**: Direct Gemini to use available tools whenever answering questions requires live data.
* **Optional Arguments & Clarification**: Instruct Gemini that optional arguments (`electionId`, `complaintId`, `unreadOnly`) must NOT be requested from the user when general questions are asked. Call tools with empty/default arguments immediately (e.g. `checkVotingEligibility({})` for "Can I vote?"). Ask clarifying questions only when mandatory inputs are missing (e.g. `title` and `description` for `submitComplaint`).
* **Result Interpretation**: Require Gemini to translate successful tool result data into warm, friendly conversational language. Ban raw JSON output, MongoDB IDs (`_id`), internal schema keys (`__v`), or system implementation details.
* **Response Style & Markdown Output**: Produce clean Markdown (bullet lists `- Item`, bold headers `**Title**`) for multi-item results like announcements and notifications.
* **Error Wording**: Convert tool execution failures into short, polite user-friendly explanations without leaking database error messages, stack traces, or technical jargon.

### 2. Gemini Function Declarations
#### [MODIFY] [toolRegistry.js]
* **Keep `getAvailableTools()` unchanged** to preserve Phase 2 tool descriptions.
* Add parameter-level descriptions within `getGeminiFunctionDeclarations()` parameters schema:
  * `checkVotingEligibility`:
    ```js
    electionId: {
      type: 'string',
      description: 'Optional election ID. Omit when the user asks generally about their voting eligibility.'
    }
    ```
  * `getComplaintStatus`:
    ```js
    complaintId: {
      type: 'string',
      description: 'Optional complaint ID. Omit when the user asks generally about their complaint statuses.'
    }
    ```
  * `getNotifications`:
    ```js
    unreadOnly: {
      type: 'boolean',
      description: 'Optional flag. Omit to retrieve all recent notifications and updates for the user.'
    }
    ```

### 3. Tool Result Handler (Error Sanitization Only)
#### [MODIFY] [toolResultHandler.js]
* Ensure `normalizeToolResult` sanitizes raw error strings (e.g., removing database stack traces or internal exception details) into clean generic error strings before passing them to Gemini.
* **Do NOT transform successful tool result data**: Legitimate data objects/arrays returned by `toolExecutor` are passed to Gemini as safe JSON payloads so Gemini can interpret them without losing business context.

### 4. React Frontend Presentation
#### [MODIFY] [FotBuddy.js]
* Update message rendering to parse and format Markdown content (bullet lists, line breaks, bold text) cleanly instead of displaying plain unformatted text or escaped characters such as `\*`.

### 5. Comprehensive Behavioral Test Suite
#### [NEW] [testPhase3AIBehavior.js]
* Build a dedicated test script in `backend/scratch/` verifying:
  1. **Voting Eligibility**: "Can I vote?" triggers `checkVotingEligibility` with `{}` (no `electionId` requested).
  2. **Complaint Status**: "What is my complaint status?" triggers `getComplaintStatus` with `{}` and yields friendly summary (no `_id` leaked).
  3. **Notifications**: "Do I have notifications?" triggers `getNotifications` with `{}` and outputs clean bullet lists.
  4. **Announcements**: Search queries select `searchAnnouncements` and return formatted results.
  5. **Formatting**: Markdown output contains properly structured lists.
  6. **Error Sanitization**: Simulated tool errors return polite user explanations without leaking backend trace details.
